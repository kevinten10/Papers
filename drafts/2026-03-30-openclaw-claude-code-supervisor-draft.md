# 给 OpenClaw 配一个 Claude Code 管家：执行者与监管者的分离

> 让写代码的 AI 和审代码的 AI 不是同一个，是我最近想通的一件事。

## 一个反直觉的发现

最近我一直在用 OpenClaw 跑自动化任务——多平台内容分发、定时推广、社区互动。系统跑起来之后，效果确实不错：从手动 1 篇/天变成了跨平台 10+ 篇/天，发布成功率稳定在 95% 以上。

但我逐渐发现了一个问题：

**OpenClaw 很擅长"做事"，但不擅长"审视自己做的事"。**

它能按照 Skill 定义精确地执行发布、评论、格式转换，但当遇到需要优化的场景——比如代码质量退化、配置冗余、Skill 之间的重复逻辑、潜在的安全隐患——它不会主动站出来说"这里有问题"。

原因很简单：**执行者和审查者不应该是同一个角色。**

这就像让一个程序员自己 review 自己的代码——他当然能做，但效果远不如让另一个人来看。

## 我的思路：Claude Code 作为外部监管者

于是我想到了一种架构：

```
┌─────────────────────────────────────────────┐
│              Claude Code（管家）               │
│                                             │
│   ┌───────────┐  ┌──────────┐  ┌─────────┐ │
│   │ Code Review│  │ Security │  │Optimize │ │
│   │   Agent   │  │  Agent   │  │  Agent  │ │
│   └─────┬─────┘  └────┬─────┘  └────┬────┘ │
│         │              │              │      │
│         └──────────────┼──────────────┘      │
│                        │                     │
│              ┌─────────▼─────────┐           │
│              │   审查报告 / 修复   │           │
│              └─────────┬─────────┘           │
└────────────────────────┼────────────────────┘
                         │
                         ▼
┌─────────────────────────────────────────────┐
│             OpenClaw（执行者）                 │
│                                             │
│   ┌──────────┐  ┌──────────┐  ┌──────────┐ │
│   │ CSDN     │  │ 知乎     │  │ 掘金     │ │
│   │ Publisher │  │ Publisher│  │ Publisher│ │
│   └──────────┘  └──────────┘  └──────────┘ │
│                                             │
│   ┌──────────┐  ┌──────────┐  ┌──────────┐ │
│   │ Moltbook │  │ Dev.to   │  │ 微信公众号 │ │

```

简单说：

- **OpenClaw** 专注于具体任务的执行——发布内容、回复评论、处理格式、定时调度
- **Claude Code** 作为外部管家——审查代码质量、发现安全隐患、优化配置、清理冗余

两者各司其职，互不干扰。

## 为什么不在 OpenClaw 内部用内置模型来做审查？

这是我最开始的做法。OpenClaw 本身可以调用 AI 模型，我试过让它在执行完任务后自己做一轮检查。

但效果并不理想，原因有三个：

### 1. 上下文污染

OpenClaw 的内置模型在执行任务时，已经积累了大量的任务上下文——平台 API 返回值、Cookie 状态、内容模板变量。当你让同一个上下文去做审查时，它很容易"灯下黑"，因为它已经默认了当前实现是合理的。

而 Claude Code 是从零开始审视你的代码。它没有执行时的先入为主，看到的就是代码本身。

### 2. 工具链差异

OpenClaw 的内置模型能调用的工具主要面向任务执行——浏览器自动化、API 调用、文件读写。

而 Claude Code 拥有完整的开发工具链：

- **代码审查**：code-reviewer、security-reviewer agent
- **重构清理**：refactor-cleaner agent，能跑 knip、depcheck 分析死代码
- **构建修复**：build-error-resolver agent
- **TDD 工作流**：tdd-guide agent，写测试、跑测试、验证覆盖率
- **架构评估**：architect agent，做系统设计层面的评审

这些能力是 OpenClaw 不具备的，也不应该具备——因为它的职责是执行，不是审查。

### 3. 模型能力的最优配置

OpenClaw 执行任务时，用 Haiku 级别的模型就足够了——快速、便宜、够用。绝大多数发布和互动任务不需要深度推理。

但审查和优化不同。它需要理解代码架构、发现潜在风险、做出重构决策。这些场景更适合 Sonnet 甚至 Opus 级别的模型。

**让对的模型做对的事**，而不是让一个模型承担所有角色。

## Claude Code 管家具体做什么

我设想的 Claude Code 管家职责，分为三个层次：

### 第一层：日常巡检

这是最基础的能力，定期对 OpenClaw 的 Skills 代码做健康检查。

**代码质量审查**：
- 检查 Skill 脚本是否有重复逻辑可以抽取
- 发现硬编码的配置值（Cookie、API Key 写死在代码里）
- 检测超过 800 行的大文件，建议拆分
- 验证错误处理是否完整——是否有 try/except 吞掉了异常

**安全扫描**：
- 扫描代码中是否泄露了 secrets
- 检查 API 调用是否做了输入验证
- 验证 Cookie 存储方式是否安全
- 检测是否存在注入风险（特别是浏览器自动化脚本中的 JS 注入）

**配置一致性**：
- 对比各 Skill 的 config.yaml，发现配置漂移
- 验证 cron 表达式是否合理（避免任务撞车）
- 检查重试策略是否一致

### 第二层：优化建议

在巡检的基础上，Claude Code 可以主动提出优化建议。

**性能优化**：
```markdown
[建议] csdn-publisher/scripts/publish.py
- 当前每次发布都重新初始化浏览器实例，耗时 ~8s
- 建议复用浏览器会话，预估可节省 60% 启动时间
- 参考 juejin-publisher 的连接池实现
```

**代码复用**：
```markdown
[建议] 发现 3 个 Skill 都实现了相似的重试逻辑
- csdn-publisher/scripts/utils.py:retry_request()
- juejin-publisher/scripts/utils.py:retry_with_backoff()
- zhihu-publisher/scripts/utils.py:exponential_retry()
→ 建议抽取为 shared/retry.py 公共模块
```

**架构改进**：
```markdown
[建议] 当前 Cookie 管理分散在各 Skill 中
- 每个 Skill 自行读取和验证 Cookie
- Cookie 过期检测逻辑重复
→ 建议建立统一的 credential-manager 模块
→ 所有 Skill 通过它获取有效凭证
→ 过期自动通知，一处管理，多处复用
```

### 第三层：自动修复

对于确定性高、风险低的问题，Claude Code 可以直接修复。

- 格式化代码、移除 unused imports
- 更新过时的依赖版本
- 修复 lint 警告
- 补全缺失的错误处理
- 更新文档（SKILL.md 与实际代码不一致时）

修复后自动提交 PR，附带变更说明，由我确认合并。

## 一种可能的工作流

把上述想法落地，我设想的日常工作流是这样的：

```
每天早上 9:00
├── Claude Code 启动日常巡检
│   ├── 并行：code-reviewer 审查所有 Skill 变更
│   ├── 并行：security-reviewer 扫描安全隐患
│   └── 并行：refactor-cleaner 分析死代码和重复
│
├── 生成巡检报告
│   ├── CRITICAL：立即修复（安全漏洞、secrets 泄露）
│   ├── HIGH：本周修复（代码质量问题）
│   ├── MEDIUM：酌情处理（优化建议）
│   └── LOW：记录备查（风格建议）
│
├── 自动修复 LOW 级别问题，提交 PR
│
└── 通知我查看报告和 PR

整天
├── OpenClaw 正常执行所有自动化任务
├── 发布、评论、互动、监控
└── 完全不受 Claude Code 巡检影响

当 OpenClaw 执行出错时
├── 错误日志自动转发给 Claude Code
├── Claude Code 分析根因
├── 提出修复方案（或直接修复）
└── OpenClaw 应用修复后恢复执行
```

核心原则：**OpenClaw 永远不停下来等 Claude Code。** 巡检是异步的、非阻塞的。就像一个管家在你工作时默默巡视房间，不打扰你，但会在你回来时告诉你哪里需要注意。

## 这背后的设计哲学

这个模式其实不是我发明的。它在软件工程和组织管理中早已有之：

### 1. 关注点分离（Separation of Concerns）

执行和审查是两种截然不同的认知模式：

- 执行需要**专注**——精确完成每一步，不被无关信息干扰
- 审查需要**全局视角**——跳出具体步骤，看到整体模式和潜在风险

让同一个系统在这两种模式之间反复切换，效率和质量都会打折。

### 2. Maker-Checker 原则

金融行业有一个经典的风控模式：做操作的人和审核操作的人必须不同。这不是因为不信任执行者，而是因为**不同视角本身就是一种安全机制**。

一个 AI Agent 审查自己的输出，就像银行让同一个柜员既操作又审核——形式上完成了流程，但实质上失去了制衡。

### 3. Unix 哲学：Do One Thing Well

OpenClaw 做好任务执行，Claude Code 做好代码质量。每个工具做一件事，然后通过明确的接口组合起来。

这比一个"什么都能做"的超级系统更可靠、更可维护、也更容易调试。

## 对独立开发者的启发

这种"执行者 + 监管者"的模式，不只是适用于 OpenClaw。

如果你是独立开发者，可能也在经历类似的困境：

- 用 AI 写了代码，但没时间 review
- 自动化脚本跑了半年，从没人检查过代码质量
- 知道应该做安全审查，但总是"下次再说"
- 项目代码越来越臃肿，但没精力重构

**给你的 AI 执行者配一个 AI 监管者，可能是最划算的质量投资。**

你不需要自己成为那个审查者——但你需要确保审查在发生。

## 写在最后

我越来越觉得，AI Agent 的未来不是造一个无所不能的超级 Agent，而是让多个专注的 Agent 各司其职、协同工作。

OpenClaw 是我的执行者，Claude Code 是我的管家。

一个负责把事情做完，一个负责确保事情做对。

这两件事，缺一不可。

而我，只需要在关键节点做最终决策。

这可能才是"AI 时代的个人效能"真正的样子——不是你变成了超人，而是你组建了一支各有所长的 AI 团队，而你是那个做判断的人。
