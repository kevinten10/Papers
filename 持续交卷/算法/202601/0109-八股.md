# I/O模型与多路复用

## I/O操作的两个阶段

### 1. 数据准备阶段（Data Preparation）

- 数据从网络到达网卡，网卡通过DMA（Direct Memory Access）技术将数据直接复制到内核缓冲区
- 这个阶段不涉及CPU参与，完全由硬件完成
- 属于"等待数据就绪"的过程

### 2. 数据复制阶段（Data Copy）

- 数据从内核缓冲区复制到用户缓冲区，进入用户态空间
- 对于JVM：由于JVM堆内存地址会因GC动态变化，无法直接与内核交互
- 需要先复制到堆外内存（Direct Memory），再复制到JVM堆内内存
- 零拷贝技术主要优化这个阶段，减少不必要的CPU拷贝操作

纠正：  
零拷贝（Zero-copy）技术的本质是尽量避免多余的数据复制操作，减少内核空间和用户空间之间的拷贝次数。在传统I/O模型中，数据通常需要经历多次复制：

### 传统I/O的数据复制流程

1. 磁盘 → 内核缓冲区（DMA拷贝）
2. 内核缓冲区 → 用户缓冲区（CPU拷贝）
3. 用户缓冲区 → Socket缓冲区（CPU拷贝）
4. Socket缓冲区 → 网卡（DMA拷贝）

共4次拷贝，其中2次CPU拷贝，2次DMA拷贝，还涉及4次上下文切换。

### 零拷贝技术的优化方案

#### 1. mmap + write

- 使用内存映射（mmap）将内核缓冲区映射到用户空间
- 减少一次CPU拷贝：磁盘 → 内核缓冲区 → Socket缓冲区 → 网卡
- 共3次拷贝（1次CPU拷贝，2次DMA拷贝）

#### 2. sendfile

- Linux 2.1引入，直接在内核空间完成数据传输
- 磁盘 → 内核缓冲区 → Socket缓冲区 → 网卡
- 共3次拷贝（1次CPU拷贝，2次DMA拷贝），但减少了上下文切换

#### 3. sendfile + DMA gather copy

- Linux 2.4优化，支持scatter-gather DMA
- 只需将文件描述符和偏移量传递给Socket缓冲区
- 磁盘 → 内核缓冲区 → 网卡（直接DMA）
- 共2次拷贝（都是DMA拷贝），真正的零拷贝

### JVM中的零拷贝

- Java NIO的FileChannel.transferTo()方法底层使用sendfile系统调用
- DirectByteBuffer使用堆外内存，避免JVM堆内存的额外拷贝
- 堆外内存地址固定，不受GC影响，可以直接与内核交互

## 堆外内存（Direct Memory）详解

### 概念与特点

- **定义**：位于JVM进程地址空间但不在JVM堆内存中的内存区域
- **分配方式**：通过JNI（Java Native Interface）直接调用malloc()分配
- **生命周期**：不受JVM GC管理，由开发者手动管理
- **地址稳定性**：内存地址固定，不会因为GC而移动

### JVM堆内 vs 堆外内存对比

#### 堆内内存（Heap Memory）

```java
// 堆内ByteBuffer
ByteBuffer buffer = ByteBuffer.allocate(1024); // 分配在JVM堆上
```

- 优点：GC自动管理，无内存泄漏风险
- 缺点：
  - GC时可能移动对象，地址不稳定
  - 读写时需要JNI调用，性能开销
  - 大对象可能触发Full GC

#### 堆外内存（Direct Memory）

```java
// 堆外ByteBuffer
ByteBuffer buffer = ByteBuffer.allocateDirect(1024); // 分配在堆外
```

- 优点：
  - 地址固定，直接与内核交互，无需额外拷贝
  - 适用于大文件/网络传输，性能更高
  - 避免GC压力，不触发Full GC
- 缺点：
  - 手动管理，容易内存泄漏
  - 分配/释放开销较大
  - 无法享受JVM内存管理的好处

### 堆外内存的管理

#### 分配与释放

```java
// 分配堆外内存
ByteBuffer directBuffer = ByteBuffer.allocateDirect(10 * 1024 * 1024); // 10MB

// 使用完毕后需要手动清理
// 方法1：依赖GC的Cleaner机制（不推荐）
directBuffer = null;
System.gc(); // 强制GC触发Cleaner

// 方法2：使用try-with-resources或手动清理
try (var channel = FileChannel.open(path)) {
    // 使用directBuffer
} // 自动清理
```

#### 内存限制

- **最大限制**：`-XX:MaxDirectMemorySize`参数，默认64MB
- **监控方式**：使用`java.nio.Bits`类的私有方法或JMX
- **泄漏检测**：堆外内存泄漏难以发现，可通过工具如VisualVM监控

### 零拷贝在Java中的实现

#### FileChannel.transferTo() 示例

```java
public void zeroCopyTransfer(File source, File target) throws IOException {
    try (FileChannel sourceChannel = FileChannel.open(source.toPath());
         FileChannel targetChannel = FileChannel.open(target.toPath(),
             StandardOpenOption.CREATE, StandardOpenOption.WRITE)) {

        long position = 0;
        long size = sourceChannel.size();

        // 使用sendfile实现零拷贝
        while (position < size) {
            long transferred = sourceChannel.transferTo(position, size - position, targetChannel);
            position += transferred;
        }
    }
}
```

#### DirectByteBuffer网络传输

```java
public void directBufferNetwork(SocketChannel channel) throws IOException {
    // 分配堆外内存
    ByteBuffer buffer = ByteBuffer.allocateDirect(64 * 1024);

    try {
        while (channel.read(buffer) > 0) {
            buffer.flip();
            // 直接使用堆外内存与内核交互，无需额外拷贝
            channel.write(buffer);
            buffer.clear();
        }
    } finally {
        // 重要：清理堆外内存
        ((DirectBuffer) buffer).cleaner().clean();
    }
}
```

### 零拷贝技术的限制与注意事项

#### 适用场景

- **文件传输**：Nginx、Apache、Kafka等
- **静态资源服务**：图片、视频等大文件
- **日志收集**：不需要修改的原始数据
- **网络代理**：数据转发场景

#### 不适用场景

- **数据处理**：需要修改数据的场景（如压缩、加密）
- **小文件传输**：零拷贝有额外开销
- **频繁读写**：堆外内存分配/释放开销大

#### 性能权衡

- **CPU使用率**：减少CPU拷贝，降低CPU占用
- **内存使用**：可能增加内存使用（内核缓冲区）
- **延迟**：减少上下文切换，降低延迟
- **吞吐量**：DMA操作效率更高，提高吞吐量

### 实际应用案例

#### Kafka零拷贝优化

- **问题**：传统模式下消息需要多次拷贝
- **解决方案**：使用FileChannel.transferTo()实现零拷贝
- **效果**：提升30-50%的传输性能

#### Netty堆外内存管理

```java
// Netty使用堆外内存优化
ByteBuf directBuffer = PooledByteBufAllocator.DEFAULT.directBuffer(1024);
try {
    // 使用directBuffer进行网络I/O
} finally {
    directBuffer.release(); // 池化管理，避免频繁分配
}
```

### 总结

零拷贝技术和堆外内存是高性能I/O的核心优化手段，通过减少不必要的内存拷贝和上下文切换来提升系统性能。但需要根据具体场景权衡使用，避免滥用导致的内存泄漏和性能反效果。

## I/O多路复用进阶

### epoll vs select/poll 的效率对比

#### 1. 监听FD数量限制

**select的限制**：

- 使用固定大小的fd_set（通常1024），由FD_SETSIZE宏定义
- 超过限制需要修改内核宏重新编译，或使用多个select
- 每次调用都需要遍历整个fd_set，时间复杂度O(n)

**poll的限制**：

- 理论上无上限，通过pollfd结构体数组指定
- 但仍然需要遍历所有fd，时间复杂度O(n)

**epoll的优势**：

- 监听FD数量理论上无上限（仅受内存限制）
- 使用红黑树管理FD集合，无需每次遍历
- 内核只返回就绪的FD，时间复杂度O(1)

#### 2. 数据结构差异

**select/poll**：

```c
// select使用位图
fd_set readfds;
FD_ZERO(&readfds);
FD_SET(sockfd, &readfds);
select(maxfd+1, &readfds, NULL, NULL, &timeout);

// poll使用数组
struct pollfd fds[MAX_FDS];
fds[0].fd = sockfd;
fds[0].events = POLLIN;
poll(fds, nfds, timeout);
```

**epoll**：

```c
// epoll使用红黑树+就绪队列
int epfd = epoll_create(1);
struct epoll_event event;
event.events = EPOLLIN;
event.data.fd = sockfd;
epoll_ctl(epfd, EPOLL_CTL_ADD, sockfd, &event);

// 等待事件
struct epoll_event events[MAX_EVENTS];
int nfds = epoll_wait(epfd, events, MAX_EVENTS, timeout);
```

#### 3. 内核空间与用户空间拷贝

**select/poll**：
- 每次调用都需要在内核和用户空间拷贝fd_set/pollfd数组
- 即使只有一个FD就绪，也要拷贝整个数组

**epoll**：
- 只在epoll_ctl添加FD时拷贝一次
- epoll_wait只返回就绪的FD，无需拷贝整个集合
- 减少了不必要的内存拷贝开销

#### 4. 性能对比总结

| 特性     | select | poll       | epoll      |
|----------|--------|------------|------------|
| FD限制   | ~1024  | 无理论上限 | 理论无上限 |
| 时间复杂度 | O(n)   | O(n)       | O(1)       |
| 拷贝次数 | 每次都拷贝 | 每次都拷贝 | 只拷贝就绪FD |
| 适用场景 | 小规模连接 | 中等规模   | 大规模高并发 |

### 同步I/O vs 异步I/O

#### 同步I/O（Synchronous I/O）

**定义**：I/O操作完成后才返回，线程在等待期间被阻塞

**特点**：
- **阻塞等待**：发起I/O请求后，线程挂起等待完成
- **简单直观**：编程模型简单，逻辑清晰
- **资源浪费**：线程阻塞期间无法处理其他任务

**分类**：

1. **同步阻塞I/O**（Blocking I/O）：read/write调用后阻塞等待
2. **同步非阻塞I/O**（Non-blocking I/O）：设置O_NONBLOCK，立即返回EWOULDBLOCK
3. **I/O多路复用**（I/O Multiplexing）：select/poll/epoll，同步等待多个FD就绪

**本质**：用户线程主动轮询或等待I/O操作完成

#### 异步I/O（Asynchronous I/O）

**定义**：发起I/O请求后立即返回，通过回调或信号通知完成

**特点**：
- **非阻塞发起**：I/O请求立即返回，不阻塞线程
- **内核完成**：内核负责整个I/O操作，用户线程无需等待
- **事件驱动**：通过回调函数或信号处理完成事件

**Linux AIO实现**：

```c
// 异步读操作
struct iocb io;
io.aio_fildes = fd;
io.aio_buf = buffer;
io.aio_nbytes = size;
io.aio_offset = offset;

// 提交异步请求
int result = io_submit(ioctx, 1, &io);

// 获取完成事件
struct io_event events[1];
io_getevents(ioctx, 1, 1, events, NULL);
```

**本质区别**：
- **同步I/O**：用户线程负责数据拷贝（内核→用户空间）
- **异步I/O**：内核负责完整I/O操作，包括数据拷贝

### epoll的LT和ET模式

#### LT模式（Level Triggered）

**工作原理**：
- 只要FD上有未处理的事件，就会不断触发
- 类似电平触发，条件满足就一直触发

**特点**：
- **编程简单**：可以只处理部分数据，剩余数据下次还会触发
- **可靠性高**：不容易丢失事件
- **性能开销**：可能产生大量重复触发

**使用示例**：

```c
// LT模式：可以分多次读取
void handle_read(int fd) {
    char buffer[1024];
    int n = read(fd, buffer, sizeof(buffer));
    if (n > 0) {
        // 即使没读完，下次epoll_wait还会触发
        process_data(buffer, n);
    }
}
```

#### ET模式（Edge Triggered）

**工作原理**：
- 只在FD状态发生变化时触发一次
- 类似边沿触发，只在上升沿或下降沿触发

**特点**：
- **高效性能**：减少重复触发，提高吞吐量
- **编程复杂**：必须一次性处理完所有数据
- **易错风险**：忘记处理完数据会导致事件丢失

**使用示例**：

```c
// ET模式：必须一次性读完
void handle_read(int fd) {
    char buffer[1024];
    while (true) {
        int n = read(fd, buffer, sizeof(buffer));
        if (n == -1) {
            if (errno == EAGAIN || errno == EWOULDBLOCK) {
                break; // 没有更多数据
            }
            // 处理错误
        } else if (n == 0) {
            // 连接关闭
            close(fd);
            break;
        } else {
            process_data(buffer, n);
        }
    }
}
```

#### LT vs ET 对比

| 特性     | LT模式 | ET模式         |
|----------|--------|----------------|
| 触发条件 | 条件满足就触发 | 状态变化时触发 |
| 编程难度 | 简单   | 复杂           |
| 性能     | 较低（重复触发） | 较高（减少系统调用） |
| 可靠性   | 高（不容易丢事件） | 需要小心处理     |
| 适用场景 | 简单应用 | 高性能服务器   |

#### ET模式使用注意事项

**1. 非阻塞设置**：

```c
// ET模式必须设置非阻塞
int flags = fcntl(fd, F_GETFL, 0);
fcntl(fd, F_SETSOCKOPT, flags | O_NONBLOCK);
```

**2. 循环读取**：

```c
// 必须在循环中读取所有数据
while ((n = read(fd, buf, sizeof(buf))) > 0) {
    // 处理数据
}
if (n == -1 && errno != EAGAIN) {
    // 处理错误
}
```

**3. 错误处理**：

- EAGAIN/EWOULDBLOCK：无数据可读，继续等待
- ECONNRESET：连接被对端重置
- ETIMEDOUT：连接超时

**4. 缓冲区管理**：

- 使用足够大的缓冲区
- 避免缓冲区溢出
- 考虑分包粘包问题

## 网络编程进阶方向

### Reactor模式：基于I/O复用的事件驱动架构

#### 模式定义

**Reactor模式**：一种事件驱动的架构模式，通过I/O多路复用监听事件，统一分发给相应的事件处理器。

#### 核心组件

**1. Reactor（反应器）**
- 负责监听I/O事件
- 使用select/poll/epoll等I/O多路复用技术
- 将就绪事件分发给对应Handler

**2. Handler（事件处理器）**
- 处理具体I/O事件
- Acceptor：处理连接事件
- Reader：处理读事件
- Writer：处理写事件

**3. Demultiplexer（事件分离器）**
- 实际的I/O多路复用实现
- select、poll、epoll等

#### Reactor模式分类

**单线程Reactor模式**：

```
Main Reactor Thread
├── 监听accept事件
├── 处理新连接
└── 分发读写事件给对应Handler
```


**多线程Reactor模式**：

```
Main Reactor Thread (Acceptor)
├── 监听accept事件
└── 创建Sub Reactor

Sub Reactor Thread (多个)
├── 监听读写事件
└── 处理业务逻辑
```


**主从Reactor模式**：

```
Main Reactor Thread
├── 监听accept事件
└── 将连接分配给Sub Reactor

Sub Reactor Threads (多个)
├── 每个线程独立监听一组连接
└── 处理读写事件
```


#### Reactor模式的优缺点

**优点**：

- **高并发**：单线程处理成千上万连接
- **资源节约**：不需要为每个连接创建线程
- **可扩展**：支持海量并发连接

**缺点**：

- **编程复杂**：异步编程思维转变
- **调试困难**：异步调用栈追踪复杂
- **学习成本**：理解事件驱动模型需要时间

### Proactor模式：异步I/O的实现模式

#### 模式定义

**Proactor模式**：一种异步I/O的架构模式，I/O操作由内核完成，用户线程通过回调处理结果。

#### 核心组件

**1. Proactor（主动器）**
- 管理异步操作
- 发起异步I/O请求
- 等待I/O完成事件

**2. Completion Handler（完成处理器）**
- 处理异步I/O完成事件
- 回调函数形式

**3. Asynchronous Operation Processor**
- 实际执行异步I/O的组件
- 通常是操作系统内核

#### Proactor模式流程

```
1. 用户线程发起异步操作
   ↓
2. Proactor将请求提交给内核
   ↓
3. 内核执行I/O操作
   ↓
4. I/O完成后通知Proactor
   ↓
5. Proactor调用完成回调
   ↓
6. 用户线程处理结果
```


#### Reactor vs Proactor 对比

| 特性         | Reactor | Proactor                     |
|--------------|---------|------------------------------|
| I/O模型     | 同步I/O | 异步I/O                     |
| 等待对象     | I/O就绪 | I/O完成                     |
| 数据拷贝     | 用户线程 | 内核完成                     |
| 实现复杂度   | 中等     | 高                           |
| 操作系统支持 | 广泛     | 有限（Windows IOCP, Linux AIO） |
| 适用场景     | 高并发网络服务 | 磁盘I/O密集应用             |

### Netty框架：基于Java NIO的高性能网络库

#### Netty概述

**Netty**：一个基于Java NIO的高性能网络框架，封装了底层I/O细节，提供易用的API。

#### 核心特性

**1. 高性能**

- 基于NIO，支持零拷贝
- 高效的内存管理（堆外内存池化）
- 支持多种序列化协议

**2. 易用性**

- 简洁的API设计
- 丰富的编解码器
- 支持多种协议（HTTP, WebSocket, TCP, UDP）

**3. 可扩展**

- 插件化架构（ChannelPipeline）
- 支持自定义协议
- 丰富的扩展点

#### Netty架构组件

**1. Bootstrap & ServerBootstrap**

```java

bootstrap.group(bossGroup, workerGroup)

         .childHandler(new ChannelInitializer<SocketChannel>() {
             @Override
             protected void initChannel(SocketChannel ch) {
                 ch.pipeline().addLast(new MyHandler());
             }
         });
```

**2. Channel & ChannelPipeline**

```java
// ChannelPipeline：责任链模式
public class MyHandler extends ChannelInboundHandlerAdapter {
    @Override
    public void channelRead(ChannelHandlerContext ctx, Object msg) {
        // 处理读事件
        ByteBuf buf = (ByteBuf) msg;
        // 业务处理
        ctx.writeAndFlush(response);
    }
}
```

**3. ByteBuf：优化的字节缓冲区**


#### Netty的Reactor实现

**Netty的事件循环**：
```java
// Boss Group：处理连接
EventLoopGroup bossGroup = new NioEventLoopGroup(1);
```

- **Pipeline**：事件在ChannelPipeline中流动，支持拦截和处理
