# 数据库

## 索引

### B+树数据结构

#### B+树的层数
- **典型结构**：根节点 -> 中间节点(可选) -> 叶子节点
- **最小层数**：2层(根节点直接连接叶子节点)
- **一般层数**：3-4层(根+1-2层中间节点+叶子节点)
- **最大层数**：通常不超过4层，足以支持数亿条数据
- **层数计算**：假设每个节点可存储200个索引键，3层可支持200³=8,000,000条记录
- B+树特点：
  - 多路平衡搜索树，所有叶子节点在同一层
  - 非叶子节点只存储索引，叶子节点存储数据
  - 叶子节点之间通过双向链表连接，支持范围查询
  - 节点大小通常为页大小(16KB)，充分利用磁盘预读特性
    - **磁盘预读原理**：磁盘I/O按页(通常4KB或16KB)为单位，即使只需要1字节也会读取整个页
    - **B+树优化**：每个节点大小等于磁盘页大小，一次I/O即可读取整个节点
    - **减少I/O次数**：相比B树，B+树在相同数据量下需要更少的磁盘访问
    - **局部性原理**：利用程序访问的局部性，一次读取的数据很可能在不久后被访问

- B+树优势：
  - 磁盘I/O效率高，减少随机访问
  - 支持范围查询和排序操作
  - 树高度低，查询复杂度稳定O(log n)
  - 适合作为数据库索引底层实现

- B+树结构图示：
```
                    [根节点]
                   /   |   \
                  /    |    \
                 /     |     \
           [10,20]  [30,40]  [50,60]
            /  |  \   /  |  \   /  |  \
           /   |   \ /   |   \/   |   \
      [1,5,8] [11,15,18] [21,25,28] [31,35,38] [41,45,48] [51,55,58]
        |        |        |        |        |        |
      ← 1 → ← 5 → ← 8 → ← 11 → ← 15 → ← 18 → ... (叶子节点双向链表)
         |        |        |        |        |        |
       数据      数据      数据      数据      数据      数据
```

- 图示说明：
  - 根节点和中间节点只存储索引键，不存储数据
  - 所有叶子节点在同一层，存储实际数据
  - 叶子节点之间通过双向链表连接，支持范围查询
  - 每个节点代表一个磁盘页(通常16KB)

- 查询过程示例图（查找值为25的数据）：
```
                    [根节点]
                   /   |   \
                  /    |    \
                 /     |     \
           [10,20]  [30,40]  [50,60]     ← 第1步：读取根节点，确定去[30,40]分支
            /  |  \   /  |  \   /  |  \
           /   |   \ /   |   \/   |   \
      [1,5,8] [11,15,18] [21,25,28] [31,35,38] [41,45,48] [51,55,58]     ← 第2步：读取[30,40]节点，确定去[21,25,28]叶子节点
        |        |        |        |        |        |
      ← 1 → ← 5 → ← 8 → ← 11 → ← 15 → ← 18 → ... (叶子节点双向链表)
         |        |        |        |        |        |
       数据      数据      数据      数据      数据      数据
                                     ↑
                                 第3步：读取叶子节点，找到25
```

- 查询分析：
  - **查找路径**：根节点 → 中间节点 → 叶子节点（最多3次磁盘I/O）
  - **范围查询**：找到起始叶子节点后，通过双向链表顺序读取后续节点
  - **I/O效率**：每次I/O读取16KB数据，包含大量索引信息，减少磁盘访问次数

- MySQL中B+树索引：
  - 主键索引：叶子节点存储完整行数据
  - 辅助索引：叶子节点存储主键值，需要回表查询
  - 组合索引：按最左前缀原则组织索引键

主键索引：特殊的唯一索引，不允许控制，一个表只能有一个主键索引
唯一索引：允许有空值
普通索引：基本索引
组合索引：多个列创建的索引，最左前缀原则
全文索引：用于全文搜索
- 原理：基于倒排索引，将文本分割成单词，建立单词到文档的映射关系
- 适用场景：博客内容、文章搜索、产品描述等大文本字段
- 支持操作：MATCH() AGAINST() 函数，支持自然语言搜索、布尔搜索、查询扩展
- 限制：只支持MyISAM和InnoDB引擎，中文需要分词插件支持

### 设计原则

最左前缀匹配：查询条件从最左列开始匹配
避免索引失效：
避免使用select *
避免在索引列上进行计算、函数操作、类型转换
避免使用not、<>、!=、is null、is not null等操作
避免使用or包含非索引列的条件

合理使用覆盖索引，查询的所有列都包含在索引中，避免回表查询

### 字段优化

整数类型尽量使用int

非负数使用unsigned

固定长度字符串使用char

可变长度字符串使用varchar
- 长度设置原则：
  - 根据实际业务需求设置，避免过度冗余
  - 考虑未来扩展性，留适当余量
  - 常用长度：50(姓名)、100(地址)、200(描述)、500(长文本)
  - 255 vs 256：255是单字节最大值，256在某些场景可能触发mediumtext
  - 建议：优先使用255以内长度，超过时考虑text类型

- 是否需要使用2的整数倍（如63、64）？
  - **存储空间**：VARCHAR是变长字符串，实际占用空间取决于内容长度，不受定义长度的影响
  - **内存对齐**：MySQL VARCHAR本身不要求2的整数倍，现代CPU内存对齐通常是8字节
  - **索引效率**：索引页16KB，字段长度影响索引条目大小，但不是决定性因素
  - **实际建议**：
    - 优先考虑业务语义：姓名用50，地址用100，描述用200等
    - 不必强求2的整数倍：50、60、80等都可接受
    - 避免过度精确：留适当余量，如手机号用20而非11
    - 性能影响很小：主要关注业务合理性而非微观优化

财务数据使用decimal而非float/double

避免使用text/blog，会降低查询性能

enum修改成本高，建议使用tinyint

## 🚀 高级索引技术

### 前缀索引
- 原理：对字符串前N个字符创建索引
- 适用场景：长文本字段，如URL、邮箱等
- 创建语法：`CREATE INDEX idx_prefix ON table(column(N))`
- 选择前缀长度：平衡索引大小和查询效率，使用`SELECT COUNT(DISTINCT LEFT(column, N))/COUNT(*) FROM table`计算选择性

### 倒排索引
- 原理：建立词语到文档ID的映射关系
- 实现方式：分词 -> 建立词典 -> 创建倒排表
- 适用场景：全文搜索、搜索引擎
- MySQL实现：FULLTEXT索引 + MATCH() AGAINST()

### 空间索引
- 原理：使用R树或四叉树等空间数据结构
- 适用场景：地理位置查询、附近的人等LBS服务
- MySQL实现：GEOMETRY类型 + SPATIAL索引

## 💭 思考题答案

### 为什么组合索引需要遵循最左前缀原则？
组合索引按照索引定义的顺序从左到右建立B+树，查询时必须从最左列开始匹配，才能利用索引的有序性。如果跳过左侧列，索引就无法发挥作用。

### 什么情况下会导致索引失效？如何避免？
索引失效情况：
1. 在索引列上进行计算、函数操作、类型转换
2. 使用NOT、<>、!=操作符
3. 使用IS NULL或IS NOT NULL
4. 使用OR连接非索引列
5. LIKE查询以通配符开头(%abc)
6. 索引列参与隐式类型转换

避免方法：
1. 避免在索引列上进行函数操作
2. 使用覆盖索引减少回表
3. 合理设计组合索引顺序
4. 注意SQL书写规范

### VARCHAR(100)和VARCHAR(10)存储相同内容时，磁盘空间占用是否相同？为什么？
不相同。VARCHAR存储变长字符串，会额外使用1-2字节记录实际长度。相同内容下，定义的长度不影响存储空间，但会影响索引效率和内存分配。建议根据实际需求设置合适长度。
