# Java并发

## 线程不安全的原理

多线程环境下线程不安全问题的根本原因是Java内存模型（JMM）中的三大特性没有得到保证：

1. **可见性问题**：现代计算机采用多级缓存架构，当多个线程运行在不同CPU核心上时，每个线程可能在自己的工作内存（CPU缓存）中维护变量副本。一个线程修改共享变量后，其他线程可能无法立即看到最新值，因为修改只存在于该线程的缓存中，未同步到主内存。

2. **原子性问题**：看似简单的操作（如i++）实际包含多个步骤（读取、计算、写入），在多线程环境下这些步骤可能被其他线程中断，导致操作不完整。例如两个线程同时执行i++，可能只增加1而不是2。

3. **有序性问题**：编译器和CPU为了优化性能，会对指令进行重排序。虽然重排序在单线程环境下不会影响结果，但在多线程环境下可能导致意外的执行顺序，破坏程序的正确性。

这些问题源于现代计算机体系结构的优化设计：多核CPU、多级缓存、指令流水线等虽然提升了性能，但也引入了内存可见性和执行顺序的不确定性。

## volatile的原理

volatile是Java提供的轻量级同步机制，它保证了变量的可见性和有序性，但不保证原子性。

### 核心特性

- **可见性**：volatile变量的修改对所有线程立即可见。当一个线程修改volatile变量时，会强制将修改后的值立即刷新到主内存；当其他线程读取该变量时，会强制从主内存重新加载最新值。
- **有序性**：volatile通过内存屏障禁止指令重排序，保证volatile变量的读写操作不会被重排序到屏障之外。
- **不保证原子性**：volatile不保证复合操作的原子性，如i++这种读-改-写操作仍然不是线程安全的。

### 底层实现机制

1. **内存屏障**：JVM在volatile变量读写时插入内存屏障指令：
   - Load Barrier（读屏障）：在volatile读操作后插入，保证后续读操作不会被重排序到屏障前
   - Store Barrier（写屏障）：在volatile写操作前插入，保证前面的写操作不会被重排序到屏障后

2. **缓存一致性协议**：volatile变量遵循MESI（Modified-Exclusive-Shared-Invalid）缓存一致性协议。当一个CPU核心修改volatile变量时，其他核心缓存中的该变量副本会被标记为无效，强制重新从主内存加载。

3. **汇编层面**：volatile变量的读写在汇编层面会生成特殊的指令序列，包含lock前缀的指令（如lock addl），该指令会锁定总线或缓存行，确保操作的原子性和可见性。

### 使用场景

- 状态标志：如boolean类型的停止标志
- 一次性安全发布：确保对象引用的可见性
- 独立观察：变量不依赖当前值（如经典的double-checked locking中的volatile）

volatile适用于不需要保证原子性的简单场景，其性能开销远小于synchronized，适合读多写少的并发场景。

## synchronized原理

synchronized 是java内置的悲观锁机制，通过对象监视器monitor保证临界区代码的原子性、可见性、有序性。

字节码层面指令，获取锁和释放锁。jvm层面基于对象监视器，每个对象关联一个监视器，线程通过竞争监视器所有权实现同步

## 线程六种状态

new 已创建但未调用
runnable 就绪和运行
blocked 等待sync锁

timed_waiting 限期等待

锁优化：为了减少传统synchronized重量级锁带来的性能开销，JDK 1.6之后引入了多种锁状态，并实现了锁的分级机制，具体包括偏向锁、轻量级锁和重量级锁。默认情况下对象处于无锁状态，当同一个线程多次进入同步块时，会升级为偏向锁，减少不必要的CAS操作，提高加锁和解锁效率。当多个线程竞争时，偏向锁会升级为轻量级锁，此时通过自旋避免线程阻塞，进一步提升性能。如果竞争更加激烈导致自旋失败，则锁会升级为重量级锁（传统的操作系统互斥量实现），此时线程会阻塞并等待锁释放。整个升级过程有清晰的路径，称为锁的升级和膨胀，目的是在不同的并发场景下权衡性能和安全性，实现锁的最优使用。

并发容器如ConcurrentHashMap（采用分段锁）和CopyOnWriteArrayList（写时复制），均为实现线程安全而设计。

底层实现方面，synchronized由JVM直接支持，依靠对象的Monitor（监视器锁）实现，其原理是在进入同步块时，JVM通过monitorenter和monitorexit字节码指令获取和释放对象锁。对象头里维护了锁的状态标记（如无锁、偏向锁、轻量级锁、重量级锁），根据竞争情况自动演化。Monitor最终通过操作系统的互斥原语（如Mutex）保障互斥和可见性。

AQS（AbstractQueuedSynchronizer，抽象队列同步器）的核心实现机制如下：

1. 线程挂起的方式：  
当有线程尝试获取同步状态（锁）失败时，AQS会把该线程包装成一个Node节点插入同步队列（一个FIFO双向链表）末尾。此时，该线程通过调用LockSupport.park()方法被挂起（阻塞），等到它的前驱节点释放同步状态时再被唤醒（通过LockSupport.unpark()），然后继续尝试获取锁。

2. 使用volatile的线程安全性保障：
   AQS内部的同步状态（如state变量）被声明为volatile类型。volatile关键字保证了两个特性：
   - 可见性：当一个线程修改了state变量的值，其他线程能立即看到最新的值。
   - 禁止指令重排序，保证有序性。  
AQS通过与CAS（Compare-And-Swap，比较并交换）原子操作结合，实现了对同步状态变量的安全控制。具体原理是：在多线程环境下，AQS内部维护的同步状态（如state变量），每一个线程在尝试修改该状态（比如加锁或释放锁）时，都会使用CAS进行一次无锁的原子性操作。CAS会比较当前内存中的实际值是否与预期值一致，只有一致时才会将其更新为新值，否则更新失败。这种机制可以有效防止多个线程同时修改同一变量带来的竞态条件，保证修改过程的原子性和可见性。

例如，当多个线程竞争锁时，每一个线程都会尝试使用CAS将state从“无锁”更改为“加锁”状态。如果只有一个线程CAS成功，则说明是该线程获得锁，其余线程CAS失败，就会进入同步队列排队等待。这样，无需加重锁的开销，也能通过硬件指令实现高效的多线程安全控制，从而完全避免了诸如读取到过期值、非原子更新等并发问题，确保线程安全。

AQS正是通过标准化"同步状态管理+线程排队与挂起唤醒"流程，为如ReentrantLock、ReentrantReadWriteLock等锁实现提供了统一高效的底层支持。

两者的本质区别是：synchronized由JVM层直接管理和优化，依靠对象头和监视器；而ReentrantLock/ReadWriteLock由Java实现，依赖AQS和队列，扩展性和功能性更强，但需要开发者手动管理锁的释放。

综上，synchronized使用简单，适合一般场景；进阶锁和并发容器则为高并发、高性能需求提供了更多选择。

## CAS原理和ABA问题

CAS（Compare-And-Swap，比较并交换）是一种乐观锁实现，通过硬件指令保证原子性操作。

### CAS原理

CAS包含三个参数：内存位置V、预期原值A、新值B。执行时会检查内存位置V的值是否等于预期原值A，如果相等则将V更新为新值B，否则不执行更新。整个过程是原子的，由CPU硬件指令保证。

### ABA问题

ABA问题是CAS的经典问题：假设线程1从内存位置V读取值为A，此时线程2也读取了A，然后线程2将V改为B，又改回A。此时线程1执行CAS时发现V仍然是A，但实际上V已经被修改过了。

**解决方案**：

1. **版本号机制**：AtomicStampedReference，通过版本号解决ABA问题
2. **使用AtomicMarkableReference**：只关心是否被修改过，不关心修改几次

## ThreadLocal原理和使用场景

ThreadLocal为每个线程提供独立的变量副本，避免线程间共享变量的竞争问题。

### 原理

ThreadLocal内部维护一个ThreadLocalMap，每个线程都有自己的Map实例。key为ThreadLocal对象弱引用，value为实际存储的值。当线程结束时，对应的Map也会被垃圾回收。

### 内存泄漏问题

由于key是弱引用，当ThreadLocal对象被回收时，key变为null但value仍然存在，导致内存泄漏。**解决方案**：使用完ThreadLocal后主动调用remove()方法。

### 使用场景

- 数据库连接管理
- Session管理
- 线程安全的日期格式化
- 避免参数传递

## 线程池相关问题

### 核心参数

- corePoolSize：核心线程数
- maximumPoolSize：最大线程数
- keepAliveTime：空闲线程存活时间
- workQueue：工作队列
- threadFactory：线程工厂
- handler：拒绝策略

### 执行流程

1. 线程数 < corePoolSize：创建新线程执行
2. 线程数 >= corePoolSize：放入队列
3. 队列满 && 线程数 < maximumPoolSize：创建新线程
4. 队列满 && 线程数 >= maximumPoolSize：执行拒绝策略

### 拒绝策略

1. AbortPolicy：抛出RejectedExecutionException
2. CallerRunsPolicy：调用者线程执行
3. DiscardOldestPolicy：丢弃最老的任务
4. DiscardPolicy：直接丢弃

### 线程池类型

- FixedThreadPool：固定大小线程池
- CachedThreadPool：可缓存线程池
- SingleThreadExecutor：单线程线程池
- ScheduledThreadPool：定时任务线程池

## ConcurrentHashMap原理

JDK 1.8之前采用分段锁（Segment），每个Segment维护一个HashTable，默认16个Segment。
JDK 1.8之后采用CAS + synchronized，摒弃分段锁，减少内存开销。采用数组+链表/红黑树结构。

### 核心特性

- **线程安全**：采用CAS和synchronized保证并发安全
- **高效并发**：读操作完全无锁，写操作只锁住要修改的节点
- **扩容机制**：采用分段迁移，避免一次性全局迁移

### put操作流程

1. 计算hash值定位数组位置
2. 如果位置为空，通过CAS设置
3. 如果位置有值，采用synchronized加锁
4. 链表长度超过8转为红黑树

## 死锁产生条件和避免

### 死锁产生的四个必要条件

1. **互斥条件**：资源只能被一个线程占用
2. **请求与保持条件**：线程持有资源的同时请求其他资源
3. **不可剥夺条件**：线程获得的资源在未使用完前不能被强制剥夺
4. **循环等待条件**：形成资源等待环路

### 避免死锁的方法

1. **破坏请求与保持条件**：一次性申请所有需要的资源
2. **破坏不可剥夺条件**：线程获取不到资源时主动释放已持有的资源
3. **破坏循环等待条件**：按序申请资源（资源编号）
4. **超时机制**：设置获取锁的超时时间

## happens-before原则

happens-before是JMM定义的两个操作间的偏序关系，如果操作A happens-before 操作B，那么A的执行结果对B可见。

### 基本规则

1. **程序顺序规则**：一个线程内，按程序顺序，前面的操作happens-before后面的操作
2. **监视器锁规则**：unlock操作happens-before后续对同一锁的lock操作
3. **volatile规则**：对volatile变量的写操作happens-before后续对该变量的读操作
4. **线程启动规则**：Thread.start() happens-before线程内任何操作
5. **线程终止规则**：线程所有操作happens-before线程终止检测
6. **中断规则**：interrupt() happens-before检测中断
7. **传递性**：A happens-before B，B happens-before C，则A happens-before C

## 阻塞队列

### 核心接口

BlockingQueue继承Queue，提供阻塞的put和take方法。

### 常见实现

1. **ArrayBlockingQueue**：基于数组的有界阻塞队列
2. **LinkedBlockingQueue**：基于链表的无界阻塞队列
3. **PriorityBlockingQueue**：支持优先级的无界阻塞队列
4. **DelayQueue**：延迟队列，元素只有到期才能被取出
5. **SynchronousQueue**：同步队列，不存储元素，直接传递

### 核心方法

- put(E e)：队列满时阻塞
- take()：队列空时阻塞
- offer(E e, long timeout, TimeUnit unit)：带超时时间的插入
- poll(long timeout, TimeUnit unit)：带超时时间的取出

## 并发工具类

### CountDownLatch

允许一个或多个线程等待其他线程完成操作。计数器初始化为N，每次countDown()减1，当计数器为0时等待的线程被唤醒。

**使用场景**：主线程等待多个子线程完成初始化。

### CyclicBarrier

允许一组线程相互等待到达某个公共屏障点。计数器初始化为N，每次await()减1，当计数器为0时所有等待线程被唤醒，可重复使用。

**使用场景**：多线程计算结果合并。

### Semaphore

信号量，用于控制同时访问特定资源的线程数量。本质是一个计数器，acquire()获取许可，release()释放许可。

**使用场景**：限流、数据库连接池等资源池管理。

### Exchanger

允许两个线程在交换点交换对象。当两个线程都到达交换点时，彼此交换数据。

**使用场景**：遗传算法中交换数据，生产者消费者模式的数据交换。
