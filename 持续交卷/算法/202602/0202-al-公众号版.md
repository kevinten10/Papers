# 2026-02-02 - AI网关日志收集系统设计

## 📄 内容概要

本文档详细介绍了1000节点K8s集群中AI模型调用网关的日志收集系统设计。系统需要处理每天约86TB的日志数据，实现秒级监控延迟，保证高可用性和成本可控。从系统架构、数据模型、技术选型到核心模块设计，提供了完整的工程实践指南。

## 一、核心挑战与指标

### 核心挑战

**海量数据**：1000节点K8s集群，每节点平均1000 QPS，单次请求平均产生1KB日志，每天产生约86TB日志数据。

**实时性**：首Token时间监控需要秒级甚至毫秒级的监控延迟，异常情况需要在秒级内发现并告警。

**高可用**：监控基础设施的任何组件故障都不能导致数据丢失或监控中断。

**成本**：TB级/天的数据量需要设计合理的保留策略和压缩算法。

### 核心指标

| 类别 | 指标 | 说明 | 计算方式 |
|------|------|------|---------|
| **调用量** | RPS（每秒请求数） | 系统吞吐量核心指标 | 总请求数 / 时间窗口 |
| | 成功率 | 服务可用性指标 | 成功请求数 / 总请求数 |
| **Token** | 输入Token | 计费核心依据 | 累加所有请求的prompt_tokens |
| | 输出Token | 计费核心依据 | 累加所有请求的completion_tokens |
| **性能** | TTFT（首Token时间） | 用户体验关键指标 | 请求开始时间 - 首Token到达时间 |
| | P50/P90/P99延迟 | 分位延迟 | 排序后对应百分位的请求延迟 |
| **质量** | 错误码分布 | 错误类型分析 | 按错误码分组统计 |

## 二、系统架构

### 分层架构

```
┌─────────────────────────────────────────────────────────────────┐
│                        查询层                                │
│  Grafana（可视化） + Prometheus（指标查询） + API（数据服务）   │
└─────────────────────────────────────────────────────────────────┘
                              ↑
┌─────────────────────────────────────────────────────────────────┐
│                        存储层                                │
│  ClickHouse（OLAP） + InfluxDB（TSDB） + S3（原始日志归档）   │
└─────────────────────────────────────────────────────────────────┘
                              ↑
┌─────────────────────────────────────────────────────────────────┐
│                        处理层                                │
│  Flink（实时流处理） + Spark（批处理） + 告警引擎             │
└─────────────────────────────────────────────────────────────────┘
                              ↑
┌─────────────────────────────────────────────────────────────────┐
│                        传输层                                │
│  Kafka（消息队列） + Pulsar（备选） + 缓冲队列                │
└─────────────────────────────────────────────────────────────────┘
                              ↑
┌─────────────────────────────────────────────────────────────────┐
│                        采集层                                │
│  OpenTelemetry Collector + Fluent Bit + 自定义Agent            │
└─────────────────────────────────────────────────────────────────┘
```

**分层设计原理**：
- **采集层**：负责从各个K8s节点采集日志，支持多种日志格式和协议
- **传输层**：作为数据流的缓冲区，解耦采集和处理，提供持久化和重放能力
- **处理层**：实时计算指标、聚合数据、检测异常、触发告警
- **存储层**：根据数据特性选择合适的存储引擎，支持高并发查询和长期归档
- **查询层**：提供统一的数据查询接口和可视化能力

### 多集群部署

**边缘集群架构**：每个K8s集群内部署一套轻量级日志采集系统，负责本地日志采集、初步聚合、本地缓存，减少跨集群传输量。

**中心集群架构**：独立的监控集群，部署完整的数据处理流水线，负责全局数据聚合、长期存储、复杂分析、告警管理。

## 四、技术选型

### 采集层：OpenTelemetry Collector

**选型理由**：CNCF托管的开源项目，已成为可观测性数据采集的行业标准，支持多种数据格式和协议，插件化架构可扩展。

**配置示例**：
```yaml
receivers:
  otlp:
    protocols:
      grpc:
      http:

processors:
  batch:
    timeout: 5s
    send_batch_size: 1024
  memory_limiter:
    limit_mib: 512

exporters:
  kafka:
    brokers: ["kafka-broker:9092"]
    topic: "ai-gateway-logs"
    encoding: "json"

service:
  pipelines:
    logs:
      receivers: [otlp]
      processors: [batch, memory_limiter]
      exporters: [kafka]
```

### 传输层：Kafka

**选型理由**：高吞吐（单节点可达百万级TPS）、消息持久化、分区机制支持水平扩展、消费者组支持并行消费。

**关键配置**：
- **分区数**：根据目标吞吐量计算，分区数 = 目标吞吐 / 单分区吞吐（10-100MB/s）
- **副本数**：至少3副本，保证数据可靠性和高可用
- **压缩算法**：使用Zstd或LZ4压缩，减少存储和网络开销

### 处理层：Flink + ClickHouse

**Flink选型理由**：流批一体、强大的状态管理、丰富的时间窗口语义、检查点机制保证故障恢复。

**ClickHouse选型理由**：列式存储适合OLAP场景、压缩率高（降低5-10倍存储成本）、向量化执行加速查询、支持高并发实时写入。

**Flink处理流程**：
```java
DataStream<LogRecord> stream = env.addSource(kafkaSource)
    .keyBy(record -> record.getModelName())
    .window(TumblingEventTimeWindows.of(Time.minutes(1)))
    .aggregate(new TokenAggregator())
    .addSink(clickHouseSink);
```

## 五、核心模块设计

### 5.1 日志解析与指标计算

**解析模块**：自动识别日志格式（JSON、键值对、自定义格式），使用正则表达式提取关键字段，自动推断字段类型并建立Schema。

**指标计算模块**：
- **原子计数器**：使用分布式原子计数器，保证并发场景下的准确性
- **累加器**：累加所有请求的Token数，支持按维度分组
- **T-Digest**：近似计算百分位数的算法，在有限内存中保持高精度
- **HyperLogLog**：基于概率的去重计数算法，内存占用极小（12KB可估算2^64个元素的基数）

**告警引擎**：
- **规则引擎**：阈值规则、趋势规则、比率规则、组合规则
- **告警收敛**：时间窗口内只触发一次告警、告警分组、告警抑制、告警升级
- **告警通知**：多通道支持（邮件、短信、电话、Slack、钉钉、企业微信）

### 5.2 数据富化

**TraceID关联**：通过TraceID关联整个请求链路的所有日志，通过SpanID关联请求的各个阶段，在Grafana中展示请求链路便于问题定位。

**维度表关联**：通过用户ID关联用户表，通过模型ID关联模型表，通过租户ID关联租户表，实时更新缓存保证数据一致性。

**缓存策略**：本地缓存减少查询开销，Redis集群缓存热点数据，采用Cache-Aside模式更新，系统启动时预加载热点数据。

## 六、高可用设计

### 各层容错

**采集层容错**：本地缓冲100MB日志，网络恢复后继续发送；优雅降级降低采样率；K8s健康检查自动重启；多实例部署避免单点故障。

**传输层容错**：Kafka Topic配置多副本，数据同时写入多个Broker；消费者组故障时自动重新分配分区；Broker故障时Leader自动切换；消息持久化到磁盘。

**处理层容错**：Flink定期保存检查点，故障时从最近的检查点恢复；分布式状态后端支持故障时状态不丢失；背压机制自动降低上游处理速度；Exactly-Once保证每条消息只处理一次。

**存储层容错**：ClickHouse配置多副本，数据同时写入多个节点；节点故障时查询自动路由到其他副本；定期备份数据到对象存储；定期校验数据完整性。

### 故障恢复

**Agent故障恢复**：K8s自动重启Pod；Agent使用本地磁盘缓冲，重启后继续发送；记录已发送的日志位置，重启后从断点继续。

**消息积压恢复**：降低采样率减少数据量；临时增加Kafka分区提高消费能力；从S3归档中补采缺失的数据；优先处理高优先级消息。

**网络分区恢复**：网络分区时Agent在本地处理和聚合数据；网络恢复后将本地聚合数据同步到中心集群；使用幂等处理避免重复数据。

## 七、性能优化

### 采集优化

**批量采集**：设置合理的批量大小（64KB或1024条），平衡延迟和吞吐；设置批量超时时间（5s）避免低流量场景延迟过高；批量数据压缩后发送减少网络开销。

**异步发送**：Agent异步发送数据不阻塞日志写入；使用内存队列缓冲待发送的数据；使用多个线程并发发送提高吞吐量。

**差异化采样**：错误日志、慢请求全量采集，正常日志按比例采样；根据系统负载动态调整采样率；基于机器学习预测日志的重要性智能采样。

### 处理优化

**并行处理**：将数据分区，每个分区独立处理；设置合理的并行度充分利用CPU资源；将多个操作链接减少数据序列化开销；将多个算子融合为一个减少数据传输。

**向量化计算**：使用SIMD指令加速计算；批量处理数据提高CPU利用率；列式存储支持向量化计算；内存对齐提高缓存命中率。

**高效算法**：使用HyperLogLog估算基数，内存占用极小；使用T-Digest计算百分位数，精度高且内存占用小；使用布隆过滤器快速判断元素是否存在；使用位图进行集合运算。

### 存储优化

**列式存储**：按列存储数据提高查询性能；列式存储压缩比高节省存储空间；查询时只读取需要的列减少IO；列式存储支持向量化查询提高查询性能。

**数据分区**：按时间分区便于按时间范围查询和数据过期清理；按哈希分区保证数据均匀分布；按范围分区便于按范围查询；组合多个分区键满足复杂查询需求。

**索引优化**：为主键和常用查询字段创建索引；为文本字段创建全文索引支持文本搜索；根据查询模式选择合适的索引类型。

## 八、成本控制

### 存储成本

**分层存储**：最近7天的数据存储在SSD保证查询性能；7-90天的数据存储在HDD平衡性能和成本；90天以上的数据存储在对象存储成本最低；自动将数据从热层迁移到冷层。

**压缩策略**：使用Zstd压缩算法，压缩比5:1；列式存储压缩比高节省存储空间；对重复值使用字典压缩进一步提高压缩比；对增量数据使用增量压缩减少压缩开销。

**保留策略**：原始日志保留7天用于故障排查；分钟级聚合保留30天，小时级聚合保留90天；天级聚合保留1年，月级聚合永久保留；定期清理过期数据释放存储空间。

### 计算成本

**弹性伸缩**：根据流量自动调整实例数，高峰期扩容，低谷期缩容；根据历史流量预测提前调整实例数；按时间段调整实例数，白天扩容，夜间缩容；在保证性能的前提下最小化实例数。

**Spot实例**：使用Spot实例，成本比按需实例低70-90%；使用多种实例类型降低中断风险；实例中断时自动迁移到其他实例；关键任务使用按需实例，非关键任务使用Spot实例。

**资源共享**：将在线任务和离线任务混部提高资源利用率；CPU和内存超卖提高资源利用率；使用cgroup隔离资源避免相互影响。

## 九、Agent可观测性

### 指标体系

**资源指标**：CPU使用率（阈值>90%告警）、内存使用率（阈值>90%告警）、磁盘使用率（阈值>80%告警）、网络使用率（阈值>90%告警）。

**应用指标**：采集速率（阈值<1000告警）、发送速率（阈值<1000告警）、队列深度（阈值持续增长告警）、发送成功率（阈值<99%告警）。

**业务指标**：完整率（阈值>99.9%告警）、时效性（阈值>1分钟告警）、质量率（阈值>99%告警）。

### 健康检查

**存活探针**：检查Agent进程是否运行，检查Agent端口是否可访问，检查失败时重启Pod，每10秒检查一次，连续3次失败后重启。

**就绪探针**：检查Agent功能是否正常，检查Agent是否能连接到Kafka，检查失败时摘除流量，每30秒检查一次，连续3次失败后摘除。

**自定义检查**：提供详细的状态接口返回Agent的运行状态，Agent定期自检并上报状态，根据多个指标计算健康评分，健康评分低于阈值时触发告警。

### 告警分级

| 级别 | 定义 | 影响范围 | 响应时间 | 通知方式 |
|------|------|----------|----------|----------|
| P0 | 进程崩溃、数据完全中断 | 服务完全不可用 | 立即响应 | 电话通知 |
| P1 | 资源使用率>90%、发送失败率>10% | 服务部分受损 | 30分钟内响应 | 即时通讯 |
| P2 | 潜在风险、延迟超标 | 服务性能下降 | 4小时内响应 | 邮件或工单 |
| P3 | 预警信息 | 暂无影响 | 1天内响应 | 汇总到日报 |

## 十、MQ设计与资源隔离

### Kafka分区策略

**分区数规划**：根据业务需求确定目标吞吐量；测试单分区的吞吐量（通常10-100MB/s）；分区数 = 目标吞吐 / 单分区吞吐；预留20-30%的余量应对流量增长。

**分区键选择**：按模型ID哈希保证同模型日志有序；按用户ID哈希保证同用户日志有序；按时间分区便于按时间范围查询；组合多个字段满足复杂查询需求。

**再平衡策略**：使用粘性分配器减少分区移动；只移动必要的分区减少影响范围；分阶段再平衡避免流量突增；监听再平衡事件处理分区变化。

### 资源隔离

**存储隔离**：不同业务使用独立Topic避免相互影响；不同Topic使用独立存储路径便于管理；为每个Topic设置磁盘配额避免磁盘被占满；不同Topic使用不同存储介质平衡性能和成本。

**网络隔离**：关键业务使用独立网卡避免网络争抢；限制每个Topic的流量避免网络拥塞；为每个Topic设置网络配额保证公平性；为关键业务设置高优先级保证服务质量。

**计算隔离**：将关键任务绑定到特定CPU核心；为不同请求设置优先级保证关键请求优先处理；为每个Topic设置限流避免资源被占满；为每个Topic设置资源配额保证公平性。

**安全隔离**：使用SASL认证保证只有授权用户可以访问；使用ACL授权控制用户可以访问的Topic；使用SSL加密保证数据传输安全；记录所有访问日志便于审计和追溯。

## 十一、总结

### 核心设计原则

1. **分层解耦**：采集→传输→处理→存储，各层独立扩展，故障隔离
   - 每层可以独立扩展，不会成为瓶颈
   - 故障不会跨层传播，影响范围可控
   - 技术选型灵活，可以根据需求选择最适合的技术

2. **边缘+中心**：边缘集群本地处理，中心集群全局聚合
   - 降低网络带宽压力，减少跨集群传输
   - 提高数据采集的实时性，本地处理延迟更低
   - 减少中心集群负载，提高整体系统容量

3. **可观测性优先**：完善的监控告警体系
   - 监控覆盖所有组件和指标，及时发现异常
   - 告警分级和收敛，避免告警风暴
   - 可视化展示，便于问题定位和趋势分析

4. **成本意识**：分层存储、弹性伸缩、缓存复用
   - 热数据高性能存储，冷数据低成本存储
   - 根据流量动态调整资源，避免资源浪费
   - 缓存热点数据，减少重复计算和查询

5. **高可用保障**：多副本、故障转移、自动恢复
   - 所有组件都有冗余，避免单点故障
   - 故障自动检测和恢复，减少人工干预
   - 数据不丢失、不重复、不乱序

### 技术栈推荐

- **采集层**：OpenTelemetry Collector（统一标准、插件化、高性能）
- **传输层**：Kafka（高吞吐、持久化、生态成熟）
- **处理层**：Flink（流批一体、状态管理、容错机制）
- **存储层**：ClickHouse（列式存储、高压缩、高性能查询）
- **查询层**：Grafana（可视化）、Prometheus（指标查询）
- **基础设施**：K8s（容器编排）、云托管服务（降低运维成本）

## 💭 总结与思考

AI网关日志收集系统是AI服务基础设施的重要组成部分，需要在**海量数据处理、实时性要求、高可用性、成本控制**之间找到最佳平衡点。

通过**分层架构设计**，各层可以独立扩展和优化，故障不会跨层传播；通过**边缘+中心的多集群部署**，降低网络带宽压力，提高数据采集的实时性；通过**完善的监控告警体系**，及时发现异常，快速定位问题；通过**分层存储和弹性伸缩**，在保证性能的前提下控制成本。

在实际项目中，需要根据具体的业务需求和资源约束，选择合适的技术方案和配置参数，持续优化系统性能和稳定性。
