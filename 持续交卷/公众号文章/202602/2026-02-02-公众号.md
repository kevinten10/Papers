## 🧮 算法题目精解

### 题目1：字符串数值提取

**问题描述**：从字符串中提取所有整数（含负数），返回最大值。

**示例**：`'afeag-123fae+023faeb+*098'` → 最大值：98

**解题思路**：使用双指针遍历字符串，识别数字和负号，解析整数并更新最大值。需要注意符号识别、数字解析和边界处理三个关键点。

**核心代码实现**：
```java
public static int findMaxNumber(String str) {
    int max = Integer.MIN_VALUE, i = 0, n = str.length();
    while (i < n) {
        if (Character.isDigit(str.charAt(i)) || 
            (str.charAt(i) == '-' && i + 1 < n && Character.isDigit(str.charAt(i + 1)))) {
            int sign = str.charAt(i) == '-' ? -1 : 1;
            if (sign == -1) i++;
            int num = 0;
            while (i < n && Character.isDigit(str.charAt(i))) {
                num = num * 10 + (str.charAt(i++) - '0');
            }
            max = Math.max(max, sign * num);
        } else {
            i++;
        }
    }
    return max;
}
```

**复杂度分析**：时间复杂度O(n)，空间复杂度O(1)

### 题目2：QPS滑动窗口限速器

**问题描述**：给定滑动窗口大小 n（秒）、QPS限速值 m、请求时间戳列表，计算被限速的请求数量。

**解题思路**：使用队列维护窗口内的请求时间戳，遍历时移除超出窗口的旧请求，判断当前窗口内请求数是否超限。

**核心代码实现**：
```java
public static int getQueuedRequestCount(int windowSize, int qpsLimit, List<Long> requests) {
    if (requests == null || requests.isEmpty()) return 0;
    Collections.sort(requests);
    Queue<Long> window = new LinkedList<>();
    int queued = 0;
    long windowMs = windowSize * 1000L;
    for (long requestTime : requests) {
        while (!window.isEmpty() && requestTime - window.peek() > windowMs) {
            window.poll();
        }
        if (window.size() < qpsLimit) {
            window.offer(requestTime);
        } else {
            queued++;
        }
    }
    return queued;
}
```

**复杂度分析**：时间复杂度O(n log n)，空间复杂度O(n)

| 题目 | 核心技巧 | 考察点 |

| 字符串数值提取 | 双指针遍历、符号识别 | 字符串处理、边界条件 |
| QPS限速器 | 滑动窗口、队列应用 | 限流算法、数据结构 |

## 🤖 AI系统设计关键问题

### 一、提高首Token响应速度

首Token响应时间（TTFT）由网络传输（10-100ms）、请求解析（1-10ms）、模型调度（0-500ms）、推理计算（10-50ms）四个主要阶段组成。

**关键优化技术**：
- **投机解码**：小模型快速生成候选Token序列，大模型一次性验证，加速效果1.5-3倍
- **KV Cache优化**：FlashAttention通过分块计算+IO感知算法减少显存占用；PagedAttention通过虚拟内存和物理内存分离支持高效共享
- **连续批处理**：动态批处理允许在执行过程中动态添加新请求和移除已完成请求

**小模型预热策略**：选择1-3B规模的小模型处理简单请求，复杂请求交给大模型。上下文传递方式包括文本追加、隐藏状态转换、表示投影层三种方式。

### 二、实时AI系统设计

**核心要求**：实时语音识别<100ms、实时翻译200-500ms、实时对话<500ms。与非实时系统相比，实时系统采用同步请求响应和流式输出模式，需要预加载模型和预留资源，支持快速故障恢复和渐进式降级。

**技术栈选型**：
- **推理框架**：TensorRT（NVIDIA官方）、ONNX Runtime（跨平台）、Hugging Face Optimum（开箱即用）
- **服务框架**：FastAPI（Python异步）、aiohttp（高性能）、Actix-web（Rust极低延迟）、Gin（Go高性能）
- **消息队列**：Kafka（大规模）、Pulsar（多租户）、Redis Streams（低延迟）、ZeroMQ（极低延迟）

### 三、Agent中的反思机制

**反思类型**：事前反思（执行动作前自我校验）、事后反思（执行动作后评估效果）、总结反思（任务完成后提炼经验）。

**ReAct框架**：标准ReAct循环为Thought → Action → Observation → 反思 → Thought，每次推理过程不仅考虑当前观察，还会回顾之前的推理和行动，分析成功和失败的原因。

### 四、上下文管理

**长上下文挑战**：位置编码外推（使用RoPE或ALiBi）、计算复杂度（O(n²)的注意力计算）、信息遗忘（模型倾向于关注序列开头和结尾）、推理成本（长上下文意味着每次推理处理更多Token）。

**滑动窗口策略**：丢弃策略（完全丢弃、重要性评分、规则优先、语义聚类）、跨窗口传递（摘要向量、向量数据库、引用关系机制）。

### 五、工具调用策略

**工具选择机制**：描述匹配（比较任务描述和工具描述的语义相似度）、基于推理的选择（在工具选择过程中加入显式推理步骤）。

**工具参数构造**：参数提取（命名实体识别、大语言模型、规则匹配）、参数验证（类型验证、范围验证、格式验证、业务规则验证）。

### 六、小模型与大模型协作

**协作模式**：蒸馏推理（小模型生成中间结果，大模型进一步推理）、级联推理（小模型先处理，置信度低则大模型重处理）、并行协作（同时处理，选择或融合结果）、混合协作（动态选择处理方式）。

**KV Cache共享**：上下文缓存（多个请求共享相同的系统提示或前缀）、前缀树索引（构建前缀树结构，高效管理具有公共前缀的请求）。

### 七、生产环境稳定性

**监控与告警体系**：基础设施（CPU、GPU、内存、磁盘、网络）、应用（请求延迟、吞吐量、错误率）、模型（推理延迟、输出质量、漂移检测）、业务（用户满意度、任务完成率、转化率）。

**告警分级**：P0（服务完全不可用，立即响应）、P1（服务部分受损，30分钟内响应）、P2（存在潜在风险，工作时间内处理）、P3（预警信息，汇总分析）。

**优雅降级策略**：功能降级（关闭非核心功能，保证核心功能可用）、质量降级（不关闭功能，降低输出质量）。

### 八、成本优化

**效果与成本平衡**：简单问答使用小模型，复杂推理使用大模型，中等任务使用中等模型。

**成本监控与分析**：成本归因（GPU成本按请求处理时间分摊，API成本直接计入调用请求）、成本可视化（展示成本趋势、成本分布、成本效率）。

### 九、多模态交互

**多模态输入处理**：图像（视觉理解+OCR+视觉定位）、语音（ASR+NLU+TTS）、视频（时间序列处理+多帧关联+音频处理）。

**旅游场景应用**：景点识别（视觉模型识别景点特征，结合地理位置信息）、菜单翻译（OCR识别菜单文字，翻译成目标语言）、虚拟导游（实时处理视频流，识别并叠加相关信息）。

## 📊 AI网关日志收集系统设计

### 一、核心挑战与指标

**核心挑战**：海量数据（1000节点K8s集群，每天产生约86TB日志数据）、实时性（秒级甚至毫秒级的监控延迟）、高可用（监控基础设施的任何组件故障都不能导致数据丢失或监控中断）、成本（TB级/天的数据量需要设计合理的保留策略和压缩算法）。

**核心指标**：调用量（RPS、成功率、失败率）、Token（输入Token、输出Token、总Token）、性能（TTFT、P50/P90/P99延迟）、质量（错误码分布、重试率、取消率）。

### 二、系统架构

**分层架构**：
- **采集层**：OpenTelemetry Collector + Fluent Bit + 自定义Agent
- **传输层**：Kafka（消息队列）+ Pulsar（备选）+ 缓冲队列
- **处理层**：Flink（实时流处理）+ Spark（批处理）+ 告警引擎
- **存储层**：ClickHouse（OLAP）+ InfluxDB（TSDB）+ S3（原始日志归档）
- **查询层**：Grafana（可视化）+ Prometheus（指标查询）+ API（数据服务）

**多集群部署**：边缘集群架构（每个K8s集群内部署一套轻量级日志采集系统）、中心集群架构（独立的监控集群，部署完整的数据处理流水线）。

### 三、数据模型

**核心日志结构**：包含log_id、timestamp、node_info、model_info、request_info、token_stats、timing_stats、status_info、metadata等字段。

**数据生命周期管理**：原始日志（7天，SSD）、分钟级（30天，SSD）、小时级（90天，HDD）、天级（1年，HDD）、月级（永久，对象存储）。

### 四、技术选型

**采集层**：OpenTelemetry Collector（CNCF托管的开源项目，已成为可观测性数据采集的行业标准）

**传输层**：Kafka（高吞吐、消息持久化、分区机制支持水平扩展、消费者组支持并行消费）

**处理层**：Flink（流批一体、强大的状态管理、丰富的时间窗口语义、检查点机制保证故障恢复）+ ClickHouse（列式存储适合OLAP场景、压缩率高、向量化执行加速查询、支持高并发实时写入）

### 五、核心模块设计

**日志解析与指标计算**：解析模块（自动识别日志格式、使用正则表达式提取关键字段）、指标计算模块（原子计数器、累加器、T-Digest、HyperLogLog）、告警引擎（规则引擎、告警收敛、告警通知）。

**数据富化**：TraceID关联（通过TraceID关联整个请求链路的所有日志）、维度表关联（通过用户ID、模型ID、租户ID关联对应表）、缓存策略（本地缓存、Redis集群缓存、Cache-Aside模式）。

### 六、高可用设计

**各层容错**：采集层容错（本地缓冲、优雅降级、K8s健康检查、多实例部署）、传输层容错（Kafka Topic配置多副本、消费者组故障时自动重新分配分区）、处理层容错（Flink定期保存检查点、分布式状态后端、背压机制、Exactly-Once）、存储层容错（ClickHouse配置多副本、节点故障时查询自动路由到其他副本）。

**故障恢复**：Agent故障恢复（K8s自动重启Pod、Agent使用本地磁盘缓冲）、消息积压恢复（降低采样率、临时增加Kafka分区）、网络分区恢复（Agent在本地处理和聚合数据、网络恢复后将本地聚合数据同步到中心集群）。

### 七、性能优化

**采集优化**：批量采集（设置合理的批量大小、批量超时时间、批量数据压缩）、异步发送（Agent异步发送数据、使用内存队列缓冲、使用多个线程并发发送）、差异化采样（错误日志、慢请求全量采集，正常日志按比例采样）。

**处理优化**：并行处理（将数据分区、设置合理的并行度、将多个操作链接、将多个算子融合）、向量化计算（使用SIMD指令加速计算、批量处理数据、列式存储支持向量化计算）、高效算法（HyperLogLog、T-Digest、布隆过滤器、位图）。

**存储优化**：列式存储（按列存储数据提高查询性能、列式存储压缩比高、查询时只读取需要的列）、数据分区（按时间分区、按哈希分区、按范围分区、组合多个分区键）、索引优化（为主键和常用查询字段创建索引、为文本字段创建全文索引）。

### 八、成本控制

**存储成本**：分层存储（热数据SSD、温数据HDD、冷数据对象存储）、压缩策略（Zstd压缩算法、列式存储压缩比高、字典压缩、增量压缩）、保留策略（原始日志保留7天、分钟级聚合保留30天、小时级聚合保留90天、天级聚合保留1年、月级聚合永久保留）。

**计算成本**：弹性伸缩（根据流量自动调整实例数、根据历史流量预测提前调整实例数）、Spot实例（使用Spot实例，成本比按需实例低70-90%）、资源共享（将在线任务和离线任务混部、CPU和内存超卖）。

### 九、Agent可观测性

**指标体系**：资源指标（CPU使用率、内存使用率、磁盘使用率、网络使用率）、应用指标（采集速率、发送速率、队列深度、发送成功率）、业务指标（完整率、时效性、质量率）。

**健康检查**：存活探针（检查Agent进程是否运行、检查Agent端口是否可访问）、就绪探针（检查Agent功能是否正常、检查Agent是否能连接到Kafka）、自定义检查（提供详细的状态接口、Agent定期自检并上报状态）。

**告警分级**：P0（进程崩溃、数据完全中断）、P1（资源使用率>90%、发送失败率>10%）、P2（潜在风险、延迟超标）、P3（预警信息）。

### 十、MQ设计与资源隔离

**Kafka分区策略**：分区数规划（根据业务需求确定目标吞吐量、测试单分区的吞吐量）、分区键选择（按模型ID哈希、按用户ID哈希、按时间分区）、再平衡策略（使用粘性分配器减少分区移动）。

**资源隔离**：存储隔离（不同业务使用独立Topic、不同Topic使用独立存储路径、为每个Topic设置磁盘配额）、网络隔离（关键业务使用独立网卡、限制每个Topic的流量、为每个Topic设置网络配额）、计算隔离（将关键任务绑定到特定CPU核心、为不同请求设置优先级）、安全隔离（使用SASL认证、使用ACL授权、使用SSL加密、记录所有访问日志）。

### 十一、总结

**核心设计原则**：
1. **分层解耦**：采集→传输→处理→存储，各层独立扩展，故障隔离
2. **边缘+中心**：边缘集群本地处理，中心集群全局聚合
3. **可观测性优先**：完善的监控告警体系
4. **成本意识**：分层存储、弹性伸缩、缓存复用
5. **高可用保障**：多副本、故障转移、自动恢复

**技术栈推荐**：
- **采集层**：OpenTelemetry Collector（统一标准、插件化、高性能）
- **传输层**：Kafka（高吞吐、持久化、生态成熟）
- **处理层**：Flink（流批一体、状态管理、容错机制）
- **存储层**：ClickHouse（列式存储、高压缩、高性能查询）
- **查询层**：Grafana（可视化）、Prometheus（指标查询）
- **基础设施**：K8s（容器编排）、云托管服务（降低运维成本）
