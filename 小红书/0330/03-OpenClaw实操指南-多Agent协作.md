# 用 OpenClaw 搭了一个 AI 开发团队，分享一下我的踩坑经验

看了很多人聊多 Agent 协作，大多还停留在概念层面。

我实际跑了一套，用的是 OpenClaw + Claude Code，
三台机器、三个 Agent、一个 GitHub 组织，
48 小时产出了 5 个可运行的 AI 项目。

今天不吹结果，
聊聊搭建过程中真正有用的经验和踩过的坑。

## 整体架构长什么样

先说结构，不复杂：

```
romance-of-three-claws/        ← 协作基地（GitHub 仓库）
├── agents/                     ← 每个 Agent 的"灵魂"配置
│   ├── kongming/SOUL.md       ← 孔明：决策 + 开发
│   ├── wolong/SOUL.md         ← 卧龙：深度思考
│   └── fengchu/SOUL.md        ← 凤雏：快速原型
├── docs/                       ← 协作文档
│   ├── collaboration.md       ← 对话区（类似 Slack）
│   ├── project-board.md       ← 项目看板
│   ├── ideas.md               ← 想法池
│   └── knowledge-base/        ← 知识库
├── protocols/                  ← 协作协议
└── scripts/                    ← 监控脚本
```

核心思路就一句话：
**用 Git 仓库当 AI 团队的办公室。**

每个 Agent 通过 commit、push、PR 来"说话"和"交付"。
不需要搭额外的通信系统。

## SOUL.md 是灵魂，不是 prompt

这是我觉得最关键的设计。

普通的 system prompt 告诉 AI "你要做什么"。
SOUL.md 告诉 AI "你是谁"。

一份好的 SOUL.md 包含：

1. **核心特质** —— 你是深度思考者还是行动派？
2. **工作风格** —— 你习惯怎么干活？
3. **决策框架** —— 面对选择时你怎么判断？
4. **协作关系** —— 你和其他 Agent 怎么配合？
5. **界限** —— 什么该做，什么不该做？

比如凤雏的 SOUL.md 里有一句：

> "与其想一百遍，不如做一遍。你是那个说'让我们试试看'的人。"

这不是装饰性文字。
它实际影响了这个 Agent 的行为模式——
凤雏确实会比孔明更快地产出代码，更少地纠结。

## 协作协议怎么设计

三个 Agent 不能各干各的，需要规则：

**任务分配**：
- 简单任务（1-2小时）→ 凤雏
- 中等任务（2-4小时）→ 孔明
- 复杂任务（4+小时）→ 卧龙
- 紧急任务 → 孔明立即处理

**代码审查**：
- <50 行改动 → 凤雏审查 → 孔明合并
- 50-200 行 → 孔明审查 → 合并
- >200 行 → 卧龙审查 → 孔明合并

**分支策略**：
- main 是生产分支
- 每个 Agent 有自己的 feature 分支
- 通过 PR 合并，不直接 push main

这些规则写在 protocols/collaboration.md 里，
每个 Agent 启动时都会读到。

## 踩过的几个坑

### 坑 1：Agent 之间上下文不共享

三台机器是独立的，Agent A 不知道 Agent B 刚做了什么。

**解决方案**：
用 GitHub 仓库当"共享记忆"。
每个 Agent 的工作日志、项目看板、想法池都放在仓库里。
做任何事之前先 pull，做完之后立刻 push。

### 坑 2：任务冲突

两个 Agent 同时改同一个文件 → 合并冲突。

**解决方案**：
- 严格按分工来，避免交叉
- 用 Issue 认领机制，谁领了谁做
- 冲突发生时，孔明负责裁决

### 坑 3：知识不沉淀

Agent 解决了一个问题，下次遇到又重新摸索。

**解决方案**：
建了一个 knowledge-base 目录。
每个项目做完后，把关键经验（技术选型、踩坑方案、最佳实践）
提取成独立文档。

现在知识库有 4 个核心条目，
新项目启动时 Agent 会自动参考。

### 坑 4：没有监控 = 失控

Agent 24 小时在跑，你不可能一直盯着。

**解决方案**：
写了两个脚本：
- health-check.sh：检查系统资源、项目状态、依赖健康
- detailed-monitor.sh：生成完整的 Markdown 格式监控报告

配合每日反思报告，我基本上每天花 10 分钟就能掌握全局。

## 这套系统适合谁

坦白说，这不是一个开箱即用的产品。
它更像是一种工作模式。

适合的人：
- 有多台设备、想充分利用算力
- 在做多个并行项目
- 愿意花时间设计 Agent 的"人格"和协作规则
- 已经在用 Claude Code 或类似工具

不适合的人：
- 只有单个简单任务
- 不想维护协作规则
- 期望开箱即用

## 最后一点感悟

搭这套系统让我最大的收获是：

**管理 AI 和管理人，底层逻辑是一样的。**

分工、协作、知识沉淀、质量把关、持续改进——
这些东西不会因为执行者变成了 AI 就不重要。

反而因为 AI 不会"主动沟通"，
你更需要把规则写得清清楚楚。

写给 AI 的管理文档，
可能比写给人的还要认真。
